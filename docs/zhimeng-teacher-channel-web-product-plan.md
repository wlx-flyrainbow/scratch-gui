# 新祥编程老师渠道与 Web 体验产品方案

## 1. 产品定位

本方案承接 `docs/zhimeng-teacher-channel-web-battle-map.md`，用于定义第一阶段要交付的产品形态。

产品目标：

> 让编程老师、KOL 或小机构拥有一个可转发的专属入口，家长打开后能低摩擦体验新祥编程、注册账号、购买年卡或 7 天陪跑包；运营能追踪来源、计算佣金和复盘孩子作品完成情况。

第一阶段产品形态：

- 新祥编程 Web 体验入口。
- 老师联名落地页。
- 推荐码和订单归因。
- 运营台人工记录与利润复盘。
- 统一账号、统一支付、统一授权、统一客服规则。

第一阶段不做完整白标，不做独立安装包，不做老师后台，不做班级管理。

## 2. 用户角色

| 角色 | 目标 | 核心需求 |
| --- | --- | --- |
| 家长 | 判断孩子是否适合编程启蒙 | 不安装也能先看、能理解价格和权益、能顺利付款开通 |
| 孩子 | 快速开始做第一个作品 | 打开即可试、路径简单、作品能保存或导出 |
| 老师/渠道 | 推荐产品并获得收益 | 有自己的专属链接、页面有署名、能解释产品、能结算佣金 |
| 运营 | 确认订单和复盘利润 | 能看到来源、套餐、佣金、交付成本、完成作品和退款风险 |
| 管理者 | 判断渠道是否值得扩大 | 能按老师维度看转化、利润、作品完成和复推意愿 |

## 3. 核心场景

### 3.1 老师转发体验链接

1. 运营为老师创建推荐码和联名页。
2. 老师把联名页发给家长。
3. 家长打开页面，看到老师署名、推荐语、作品案例和价格。
4. 家长点击“在线体验”，进入 Web 体验入口。
5. 家长或孩子完成注册/登录。
6. 未付费用户进入有限体验，付费用户进入完整基础编辑器。
7. 家长从 Web 或桌面订阅入口创建订单。
8. 运营确认付款并开通授权。
9. 订单归属到老师推荐码。

### 3.2 老师现场演示

1. 老师打开自己的联名页。
2. 点击 Web 体验入口，现场演示一个入门作品。
3. 家长扫码或打开同一链接。
4. 家长注册后继续体验或购买。

### 3.3 7 天陪跑包转化

1. 家长购买年卡或体验后，页面推荐 7 天项目陪跑包。
2. 运营在订单里记录老师来源、佣金和交付成本。
3. 孩子完成第一个作品后，运营收集截图和反馈。
4. 老师推荐效果按付款、作品完成和退款风险复盘。

## 4. 第一版功能范围

### 4.1 老师联名页

页面目标：让老师有推广身份，让家长理解产品和信任来源。

第一版字段：

| 字段 | 说明 |
| --- | --- |
| teacher_id | 老师/机构内部 ID |
| referrer_code | 推荐码 |
| display_name | 页面展示名 |
| avatar_or_logo_url | 老师头像或机构 Logo |
| intro | 老师简介 |
| recommendation | 老师推荐语 |
| landing_page_id | 联名页标识 |
| enabled | 是否启用 |

页面模块：

- 顶部展示 `新祥编程 x XX老师`。
- 老师头像或机构 Logo。
- 老师推荐语。
- 产品一句话定位：少儿创意编程启蒙。
- 适合年龄：6-10 岁，首发重点观察 6-8 岁。
- 作品案例：会说话的小角色、生日祝福动画、接水果小游戏。
- 套餐：199 元家庭年卡、699 元 7 天项目陪跑包。
- 按钮：在线体验、下载桌面端、咨询开通。
- FAQ：是否 Scratch 官方、是否直播课、是否需要安装、付款后如何开通。

第一版限制：

- 不允许老师修改新祥编程主品牌。
- 不允许老师隐藏 AGPL 和 Scratch 关系说明。
- 不允许老师自定义价格和承诺。
- 不允许老师上传未经审核的宣传语。

### 4.2 Web 体验入口

页面目标：让家长不安装也能体验，降低老师推广成本。

第一版能力：

- 打开 Web 编辑器。
- 注册和登录。
- 拉取服务端授权状态。
- 未付费用户有限体验。
- 已开通用户完整使用基础编辑器。
- 支持本地导入 `.sb3`。
- 支持导出 `.sb3` 到本地。
- 有订阅/购买入口。

第一版不做：

- 云保存。
- 作品社区。
- 班级管理。
- 老师布置作业。
- Web 端完整课程系统。
- 多租户品牌隔离。

有限体验建议：

- 允许打开编辑器和示例项目。
- 允许孩子尝试积木和角色。
- 可限制保存、导出、项目数量或使用时长中的一项，具体以实现成本和体验损耗评估为准。
- 限制必须由服务端授权状态驱动，不能只靠前端按钮隐藏。

### 4.3 推荐码与订单归因

第一版可以先使用 URL 参数和人工录入，不急于做完整渠道后台。

URL 示例：

```text
https://zhimeng.codevalley.cn/t/teacher-a
https://zhimeng.codevalley.cn/app?ref=teacher_a
https://zhimeng.codevalley.cn/purchase.html?ref=teacher_a
```

订单需记录：

| 字段 | 说明 |
| --- | --- |
| referrer_code | 推荐码 |
| landing_page_id | 联名页 ID |
| source_type | KOL/老师、渠道、转介绍等 |
| package_type | 年卡、陪跑包、渠道包 |
| commission_cents | 佣金 |
| attribution_note | 归因备注 |

归因规则：

- 用户从联名页进入时，优先写入 URL 推荐码。
- 如果用户付款截图或客服沟通中提供老师来源，运营可人工补录。
- 佣金按最终确认付款订单计算。
- 退款订单不计入有效佣金，或按合作规则扣回。

### 4.4 运营台能力

第一版目标：不做老师后台，先让运营能管理来源和利润。

需要支持：

- 查看订单来源。
- 记录推荐码和老师/机构名。
- 记录佣金、获客成本、交付成本、客服成本。
- 记录第一个作品是否完成。
- 记录退款风险和下次跟进。
- 按老师来源手工汇总付款数和佣金。

已有基础：

- `website/ops.html` 已有来源、套餐、佣金、成本、利润和跟进字段。
- `docs/zhimeng-seed-user-tracking.csv` 已新增推荐码、老师/机构、联名页 ID、Web 体验字段。

### 4.5 前端与运营端联动契约

老师渠道不是单独做一个前端页面。联名页、Web 体验、购买页、后端订单和运营台必须共享同一条归因链路。

端到端链路：

| 步骤 | 前端动作 | 后端/运营动作 | 必须保留的数据 |
| --- | --- | --- | --- |
| 1 | 家长打开 `/t/:teacherSlug` | 查询老师联名配置 | teacher_id、referrer_code、landing_page_id |
| 2 | 点击在线体验或下载桌面端 | 前端把推荐码带到目标链接 | ref、landing_page_id、source_type |
| 3 | 注册/登录 | 账号可记录首次来源或最近来源 | user_id、first_referrer_code、latest_referrer_code |
| 4 | 创建订单 | `/order/create` 接收来源字段 | order_id、plan、channel、referrer_code |
| 5 | 提交付款凭证 | 订单保留付款证据和来源 | payment_proof、referrer_code |
| 6 | 运营确认到账 | `ops.html` 展示并允许补录来源 | operator、paid_at、commission_cents |
| 7 | 开通授权 | 授权状态回到 Web/客户端 | entitlement_status、plan、expires_at |
| 8 | 作品跟进 | 运营记录作品完成和交付成本 | first_project_done、delivery_cost_cents |
| 9 | 佣金复盘 | 按老师维度汇总成交和利润 | paid_orders、refunds、estimated_profit |

前端必须做到：

- 联名页、Web 体验页、购买页之间传递 `referrer_code` 和 `landing_page_id`。
- 页面跳转不能丢失来源参数；必要时可短期保存到浏览器本地状态。
- 显示的老师名称、Logo、推荐语只能来自已审核配置。
- Web 体验页展示的授权状态必须来自服务端，不用前端状态伪造开通。
- 购买入口进入 `/order/create` 时必须带上当前来源字段。

后端与运营台必须做到：

- 订单创建接口接受并保存来源字段。
- 运营台能查看来源，也能在客服确认后人工补录或修正来源。
- 运营台修改来源必须进入订单审计备注，保留操作者和原因。
- 佣金只基于已确认付款且未退款的订单计算。
- 退款、冻结、争议订单必须能影响老师维度的有效佣金和利润复盘。

验收口径：

- 从老师联名页进入、注册、创建订单、付款确认后，运营台能看到老师来源。
- 如果来源参数在某一步丢失，运营能通过订单备注手工补录，并能在复盘表中体现。
- 前端看到的开通状态与运营台确认后的授权状态一致。
- 老师维度能汇总：打开数、注册数、订单数、付款数、佣金、完成第一个作品数和退款风险。

## 5. 信息架构

第一阶段建议页面：

| 页面 | 路径建议 | 用户 | 说明 |
| --- | --- | --- | --- |
| 老师联名页 | `/t/:teacherSlug` | 家长、老师 | 对外推广页 |
| Web 体验入口 | `/app` | 家长、孩子 | 浏览器打开编辑器 |
| 订阅/购买页 | `/purchase.html` 或客户端订阅页 | 家长 | 创建订单和提交凭证 |
| 运营确认页 | `/ops.html` | 运营 | 确认到账、记录来源和成本 |
| 渠道招募页 | 后置 | 老师/机构 | 第 5 阶段再做 |

## 6. MVP 验收标准

### 6.1 功能验收

- 老师能拿到一个专属联名链接。
- 家长打开联名页能看到老师信息、产品说明、价格和 FAQ。
- 家长能从联名页进入 Web 体验。
- Web 体验能完成注册/登录、授权拉取和基础编辑器访问。
- 用户能从 Web 体验或购买页创建订单。
- 订单能记录老师来源或由运营补录老师来源。
- 运营能记录佣金和成本。

### 6.2 业务验收

| 指标 | 目标 |
| --- | ---: |
| 试销老师 | 3-5 位 |
| 每位老师触达家庭 | 5-10 个 |
| 老师链接打开率 | >= 60% |
| Web 打开到注册率 | >= 30% |
| 注册到创建订单率 | >= 20% |
| 每位老师真实付款家庭 | >= 2 个或明确证明不适合 |
| 付款家庭完成第一个作品 | >= 50% |
| 老师推荐订单利润 | 扣除佣金和交付成本后为正 |

## 7. 版本拆分

### V0：手工联名验证

目标：不开发复杂系统，先验证老师是否愿意推。

范围：

- 手工创建 3-5 个联名页。
- 使用 URL 参数或表格记录推荐码。
- 运营人工归因和结算。
- Web 入口可以先使用现有构建能力做体验入口。

通过条件：

- 有老师愿意真实转发。
- 家长能打开体验。
- 有真实付款或明确流失原因。

### V1：Web 体验和订单归因

目标：把转化链路跑顺。

范围：

- Web 体验入口正式接入登录、授权和购买入口。
- 推荐码贯穿联名页、Web 入口和购买页。
- 运营台可查看和编辑来源。
- 形成 7 天老师试销复盘。

通过条件：

- 至少 3 位老师完成一轮试销。
- 老师来源订单能计算佣金和利润。
- 安装问题导致的流失明显下降。

### V2：渠道包标准化

目标：从老师推荐升级为渠道包。

范围：

- 渠道材料包。
- 4999 元渠道/机构启动包。
- 联名页模板化。
- 项目材料和讲解稿标准化。

通过条件：

- 成交 1-2 个渠道包。
- 单渠道 30 天内能带来追加家庭用户。

### V3：项目包配置

目标：满足老师内容差异化。

范围：

- 项目包名称和封面。
- 3-5 个作品任务。
- 老师署名报告。
- 结业截图或作品展示页。

通过条件：

- 自定义项目包提升作品完成率。
- 老师愿意续费或持续带单。

### V4：白标/OEM 评估

目标：只给愿意付费的机构做重定制。

范围：

- 独立报价。
- 品牌、售后、退款、数据和 AGPL 责任确认。
- 安装包名称、图标、签名、官网、客服和更新链路评估。

启动条件：

- 单机构年服务费 >= 9999 元，或单机构预付名额 >= 100 个，或定制费覆盖开发、测试、签名、发布和维护成本。

## 8. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 老师把产品说成 Scratch 官方 | 联名页固定 Scratch 关系说明，不允许老师覆盖 |
| 家长误以为是直播课或一对一课 | FAQ 明确不是直播课、不是长期一对一教学 |
| 佣金吃掉年卡利润 | 年卡佣金设上限，重点推动 699 陪跑包和渠道包 |
| Web 体验影响桌面端定位 | Web 只做低摩擦体验和轻创作，桌面端继续承接稳定交付 |
| 完整白标拖慢 MVP | 白标/OEM 放到 V4，必须有付费机构或最低销量 |
| 老师宣传语不可控 | 第一版只允许审核后的推荐语和素材 |
